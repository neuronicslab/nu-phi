    How ν-Φ works¶

    ν-Φ is a 32-channel biosignal acquisition board for EEG and EMG. It runs on a dual-core processor. Most boards share both cores between everything they do. ν-Φ gives each core one job, and draws a hard line between them.

    Where the signal comes from¶

    The board's inputs can be driven in three ways:

    • Electrodes. Surface electrodes for EEG or EMG, connected to the analog front end.
    • A DAC or signal generator. A known analog signal on the same inputs, to test the whole chain from amplifier to result.
    • The PC. Recorded or synthetic data streamed over Wi-Fi or USB straight into the processing core, with the analog front end bypassed.

    The front end is four ADS1299 converters, 8 channels each. The ADS1299 is a general biopotential converter, so EEG and EMG use the same hardware; the difference is the gain, sample rate and montage, which are all settings.

    Core 0: acquisition¶

    The first core belongs to the board. It reads the four converters, gives every sample a sequence number and the current event marker, and publishes it exactly once. It also owns the links to the PC, over Wi-Fi or the USB cable, and sends everything that leaves the board in one ordered stream.

    This core never waits for anything running on the other one. That is the rule the whole design is built around.

    Core 1: processing and edge ML¶

    The second core runs apps. An app is a small program that:

    1. reads samples as they are published, at its own pace;
    2. processes them however it likes: filters, envelopes, windows, features, models;
    3. reports results, which the board sends to the PC alongside the data.

    An app receives the raw signal from all 32 channels. The board applies no filtering of its own, so the processing is entirely the app's. Several apps can run at once, and each one sees every sample.

    When the data comes from the PC instead of the converters, apps see it exactly as they would see live samples. That makes it possible to develop and test an algorithm before any recording.

    One contract between them¶

    An app sees the board through a single header file: the contract. It holds a dozen functions, for reading samples, reading the current sample rate and gain, describing the app, and reporting results. Adding an app changes nothing in the board's code.

    Apps report results in four shapes:

    Shape What it carries Typical use
    Class a classification, up to 4 class scores a detected state or gesture
    Signal processed channels in microvolts a filtered signal
    Vector up to 32 numbers, tagged with a kind band powers, EMG envelopes, a feature set
    Your own up to 96 bytes in a layout you define anything else

    The contract carries a version number. Each app records the version it was built against, and the board checks every app before starting it. An app built for an incompatible version is refused and named, both in the board's log and in what it reports to the PC. The other apps keep running.

    When an app falls behind¶

    Samples wait for an app in a buffer of 256 samples. If an app falls further behind than that, it loses its oldest samples, and the loss is counted against that app alone. The recording and every other app carry on untouched.

    That buffer gives each app a deadline, set by the sample rate:

    Sample rate How far an app may fall behind
    250 samples/s 1.02 s
    500 samples/s 512 ms
    1000 samples/s 256 ms
    2000 samples/s 128 ms

    EMG is usually recorded at the higher rates, so an EMG app has less slack than an EEG app at 250 samples/s. The board's health reports show dropped and missed samples at all times, so you can check that an app has not disturbed the recording: if those counters stay at zero while it runs, it did not.

    Controlling the board¶

    Everything about how the board runs, from the sample rate to what it streams, is a setting you change from the ν-Φ app on your PC, without rebuilding anything.

    • The board decides. The PC asks for a change. The board checks the whole resulting configuration, applies it or refuses it with a reason, and reports what it is now actually doing. The PC always shows the board's report, never its own guess.
    • Presets live on the board. A role such as Participant or Noise floor is one command, and the board expands it the same way for every client.
    • Big changes need the cable. Settings that restart the board can be made only over USB, so nothing that interrupts a recording can happen over the air.
    • Settings are recorded with the data. Every recording saves the board's settings and firmware identity, with a new entry whenever a setting changes, so you can always tell how a file was recorded.

    Why it is built this way¶

    In research recordings the expensive failure is quiet: data that looks fine but isn't. ν-Φ is designed so that problems are loud instead. A slow app loses its own samples and says so. A mismatched app is refused by name. And the board identifies its firmware to the PC, so every file can be traced to the build that made it.
